N-gram Embedding

Trace token n-grams through a toy hash table and understand collisions, learned vectors, and offloading.

A phrasebook stores useful representations of short patterns. Instead of making a large network reconstruct every familiar local pattern, look up a compact entry and combine it with the token’s representation.

A token alone loses its neighbors

A token embedding maps a token ID to a vector. A bigram uses two consecutive IDs, and a trigram uses three. These are token sequences, not necessarily whole words. A causal lookup at position t can use the IDs ending at t; it must not consult the unknown token at t+1.

Address first, learn the contents

In a hash-addressed design, a deterministic function maps the short ID sequence to a table row. The row contains learned numbers, updated through training. The hash is an address calculation, not a database of human-readable facts. The toy polynomial hash here demonstrates addressing only and is not the official hash function.

Collisions and generalization

A finite table can map different sequences to the same row. This is a collision, and it means that row must serve more than one pattern. Enlarging a table changes the collision tradeoff but costs memory. Surrounding network computation can still distinguish contexts; one shared row does not make entire model outputs identical.

Why lookup changes the memory tradeoff

A lookup reads selected rows instead of running every row through a matrix multiplication. A large table can therefore add capacity with relatively little arithmetic. Moving requested rows from host RAM still consumes bandwidth and adds latency. Prefetching may overlap that transfer with other work, but a missed prefetch or a slow link can expose the delay.

Worked example

For token IDs [1, 2] in eight rows: h becomes 1, then (31 + 2) mod 8 = 1. For [1, 10], it is also 1: a collision. Reversing the first sequence to [2, 1] yields 7. Real token IDs and learned tables are much larger.
